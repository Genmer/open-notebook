## 背景

「来源标注系统」（划线 + 批注 + 阅读地图，四期路线 MVP/P1/P2/P3）的评审修订终稿遗留 18 项开放问题，经产品复核、技术复核与一致性复核后由维护者授权全权裁决，本记录固化最终裁决集——开放问题清零（leftTbd 为空），规划随之定稿。

## 裁决（18 项）

> 逐项含问题/裁决/理由/影响期/落选方案；「落点」指向[定稿规划](../plans/source-annotation-plan.md)章节。标注【复核修订】表示本裁决在复核环节修订过评审修订终稿的拟定答案。

### 裁决 1（MVP）：页级路由取代全册二元——真题册文件性质的判定方式

- **问题**：611 页真题册是否为文本版 PDF（非扫描件）？直接决定 MVP 主路径是划词还是降级预案（矩形框选）提前转正。（产品复核 high：原拟定裁决的 80% 阈值把交互做成全册级二元切换，混排书的文本页也被迫用框选；一致性复核：扫描分支「TextLayer 仍交付」与 §5.6 换范围语义冲突）
- **裁决**【复核修订】：交互路由永远按页判定，与全册文件性质解耦：有文本层的页出划词浮条；无文本层的页 MVP 期出 §3.1 既定 inline 提示条（「此页无文本层（扫描页）：文字划线不可用，框选批注将在下一期支持」），P1 期框选工具条交付后自然补全页级路由。全册抽样检测（12 页均匀抽样 getTextContent 非空占比）只决定两件事：① <20% 文本页（扫描为主）→ 触发 §5.6 换范围：矩形框选+quads 转正为真题册 MVP 主路径，TextLayer 整体移 P1 重攻（严格换范围语义，+3-5 人日重排，口径不变）；② 20%-80%（混排）→ 维持划词主路径 + 扫描页提示，发布说明与 dogfood 记录明示扫描页占比与 P1 框选预期；③ ≥80% → 正常主路径。§5.6 三条技术失败判据独立触发换范围，与文件性质无关。MVP 验收①改为「真题册文本页划词持久化（翻页/刷新仍在）；若走换范围分支则按框选主路径验收」。补验截止门（采纳产品复核 missing）：真实真题册上的 spike 判定与验收①未补跑前，MVP 不得标记完成；文件不可得时技术判据可用任意 ≥100 页文本 PDF 顶替，但截止门不豁免。
- **理由**：采纳产品复核的核心——文件性质不是 §5.6 意义上的技术失败，不该触发全册交互降级；页级 getTextContent 判空本就要做，路由成本 ≈0，混排书的文本页必须正常划词。采纳一致性复核：换范围分支下 TextLayer 整体移 P1，删除「仍交付服务其他源」的歧义表述，+3-5 维持换范围语义。部分反驳产品复核建议的后半（扫描页框选工具条进 MVP）：判空路由 ≈0 成本成立，但框选工具条/矩形选区/虚线框渲染/quote 求交是整套新交互（约 1.5-2 人日），且 MVP 前端分项加总已达 10-11（见裁决 3），再加将击穿预算；§3.1 提示条已做非静默的预期管理，框选 P1 兜底排期不变。补验截止门防止「文件不可得」兜底分支让 MVP 在核心验收未对真实材料执行的情况下收尾。
- **落选**：等待用户提供样本页（阻塞 MVP 启动，用户已授权全权裁决）；全册级二元切换（80% 阈值方案：混排书文本页被迫框选，TextLayer 技术可用却不用）；扫描页框选工具条进 MVP（约 1.5-2 人日新交互，MVP 分项已 10-11 触顶）；MVP 同时全量交付双路径并以双路径验收（双倍交互与测试面积，与 §5.6 换范围语义冲突）。
- **落点**：规划 §3.1、§5.6（三分支 + 补验截止门）、§7 MVP 验收①、§8#8。（执行澄清 2026-10-03 独立复核补：换范围分支下 §3.1 扫描页提示条不渲染——该分支框选即当期主路径，逐任务变更见 [MVP 任务清单](../plans/source-annotation-mvp-tasks.md) §6.1 分支对照表。）

### 裁决 2（P1）：痕迹栏与目录条件互斥 + 沟槽豁免

- **问题**：右侧痕迹栏与左侧目录 overlay 同开的宽度取舍：终稿裁决互斥。（产品复核 low：互斥无条件适用于所有屏宽，1920px+ 外接屏被迫二选一；沟槽态是否参与互斥未说明；自动收起时批注消失可能被误读为丢失）
- **裁决**【复核修订】：① 16px 沟槽态不参与互斥（常驻，与目录同开无宽度压力）；② 256px 面板态与目录互斥仅在 viewer 容器剩余阅读宽度 <900px 时生效（按容器实际宽度动态判定，不用屏宽 media query——容器宽度才是阅读面真实约束），≥900px 允许同开；③ 面板态被目录自动收起时，目录面板顶部显示一行轻提示「批注栏已收起」（消除「批注丢了」误判）。成本仍 <0.5 人日。
- **理由**：采纳产品复核三点：已核实 `PdfSourceViewer.tsx:374` 目录为 w-64（256px）absolute overlay，1920px+ 下 256+256 同开确实放得下，无条件互斥是过度限制，改按容器剩余宽度动态判定（阈值 900px：611 页 A4 在此宽度下常用缩放可读）；沟槽 16px 本就为常驻设计，参与互斥无依据；收起提示消除资产丢失错觉，与「痕迹是资产」一致。
- **落选**：无条件互斥（终稿原裁决：1920px+ 外接屏被过度限制）；同开+可折叠+缩窄的第三宽度形态（状态机复杂度与窄栏可用性双输）；沟槽态也参与互斥（16px 无宽度压力，互斥无意义）。
- **落点**：规划 §3.3、§4.5、§8#14。

### 裁决 3（全程）：工期标称对账上调 + 减压顺序重排 + 任务清单补项

- **问题**：工期与风险预算是否接受（终稿口径）：MVP 前端 8-10 + 后端 3-4.5 人日；P1 前端 7.5-9.5 + 后端 1；P2 前端 6.5-8 + 后端 1.5-2。（一致性复核 medium：三期前端分项加总 10-11 / 8.5-10 / 7.25-9.25 均高于标称；产品复核 low：减压第一刀砍测试深度会伤数据完整性；一致性复核 low：与裁决 5 砍序无优先级）
- **裁决**【复核修订】：① 标称对齐分项加总（采纳一致性复核算术核实）：MVP 前端 10-11（原 8-10）、P1 前端 8.5-10（原 7.5-9.5）、P2 前端 7.25-9.25（原 6.5-8）；后端三期维持不变（复核确认分项与标称一致）。超支 >20% 的基线以新标称中值计。② 减压顺序修订（采纳产品复核）：任一期超支 >20% 时 → 先顺延工期 → 再压缩非数据完整性类测试深度；数据完整性/资产保留类测试（export→import round-trip、备份结构校验、坐标换算纯函数边界、last-write-wins 语义）任何情况下不压缩；各期验收条目对应测试一律不动。③ 与 P1 砍序的优先级（采纳一致性复核）：P1 超支先适用裁决 5 的特例砍序，仍不足再适用本条全程规则。④ TextLayer spike 失败换范围重排 +3-5 人口径不变。MVP 任务清单补项（F1 补第 4 项，其余维持）：【前端】F1 TextLayer spike：§5.6 三判据 + 12 页抽样文件性质检测（含页级路由表落地）+ WCAG 对比度/坐标往返两项复测 + SurrealDB 嵌套字段索引/ORDER BY 能力断言验证（§8#16，结果只影响平铺字段可否简化，不影响交付）→ 出路径裁定；F2 裸 canvas 改 relative wrapper + TextLayer 集成；F3 选区→锚点换算纯函数 + vitest；F4 SVG 标注 overlay；F5 选区浮条（8 键、fixed、150ms 防抖重现、翻转）；F6 hover 批注卡 + pin 编辑态；F7 按页懒加载 + memo；F8 扫描页 inline 提示条（页级路由入口）；F9 删除源确认对话框标注计数；F10 i18n 键名一次定稿 + 14 locale 同 PR；F11 vitest 集成测试。【后端】B1 迁移 33 + async_migrate.py 双列表注册；B2 域模型；B3 CRUD + settings 路由 + main.py 注册；B4 四处导出注册；B5 源删除备份 JSON（钩子落点见裁决 8）；B6 pytest（CRUD、round-trip、备份结构校验）。任务粒度拆解见 [MVP 任务清单](../plans/source-annotation-mvp-tasks.md)。
- **理由**：采纳一致性复核：分项加总与标称失配是终稿自身算术问题（逐项核算确认：MVP 2+2+2+1.5+(0.5~1)+(1~1.5)+1=10~11，P1、P2 同），无说明的折减就是隐性低估，按分项对齐并撤销旧标称，避免「开工即触顶自己的 >20% 超支规则」。采纳产品复核：「刷新不丢/误删可恢复」是本功能的用户信任底线，数据完整性类测试列为不可压缩豁免，且顺延工期优于砍测试（宁可晚不可坏）。
- **落选**：维持旧标称 8-10/7.5-9.5/6.5-8（与分项失配，开工即触顶超支规则）；全面追加 20% 缓冲（伪精度，用户要的是拍板不是保守）；超支时先砍测试深度（原顺序下数据完整性测试首当其冲，恰是最不该省的地方）；超支时砍备份/导出注册等防护项（违反「痕迹是资产」）。
- **落点**：规划 §7 头注与各期估算；[MVP 任务清单](../plans/source-annotation-mvp-tasks.md) 全文。

### 裁决 4（P1）：解析视图 v1 持久性弱于 PDF——接受，不加版本化锚

- **问题**：解析视图 v1 持久性弱于 PDF（重跑解析即锚点漂移、降级孤儿态）是否接受？不可接受则 P1 需增加解析快照版本化锚点（约 +2 人日）。
- **裁决**：接受，P1 不加解析快照版本化锚（+2 人日移出）。升级触发条件定死：P2 dogfood（规划 §1.6 清单）或真实用户反馈中出现「单次重跑解析导致 >10% 标注失锚且影响使用」，则版本化锚插队 P3 首位（估算 2 人日不变），届时补 ADR。（本轮复核无意见，维持拟定裁决。）
- **理由**：三段锚 + 三级重锚 + orphaned 显式态的最坏结果是「显式失锚但数据保留、可重新框选」（§3.4-C、§5.3 quote 冻结规则），不违反「痕迹是资产」；备考材料重跑解析是低频动作；版本化锚只在高频重跑场景有收益，为未证实场景预付 2 人日挤占已扩容的 P1 不划算。设触发条件是为避免「接受」变「永远不做」的悬空。
- **落选**：P1 直接加版本化锚（为低频场景预付成本）；接受但不设升级触发条件（悬空表述）。
- **落点**：规划 §5.3、§7 P3 候选池、§8#3。

### 裁决 5（P1）：P1 范围扩容锁定 + 特例砍序优先于全程规则

- **问题**：P1 范围扩容（增补最简标注列表 + 最简 MD/JSON 导出，共 +1.5-2 人日，为的是「重读更省力」前两期即部分兑现）是否接受？（一致性复核 low：本条砍序与全程减压规则未声明优先级）
- **裁决**【复核修订】：接受扩容并锁定：最简「本源标注列表」+ 最简 MD/JSON 导出留 P1（+1.5-2 人日）。本条为工期裁决（裁决 3）在 P1 的特例且优先适用：P1 超支时砍序 = ① 快捷键 H/C/1-5/W-S 砍掉顺延 P2（0.5 人日）→ ② 仍不足适用全程规则（顺延工期→压非数据完整性测试）；无障碍键盘路径（P1 验收⑤）与最简列表/导出任何情况下不可砍。
- **理由**：北极星判据要求读回能力前两期兑现，纯写入两期会让标注功能连续两个迭代零回报（评审 P9 已判为规划缺陷）；扩容两项技术风险低。采纳一致性复核意见补声明优先级：快捷键是效率增强非能力缺口，故特例砍序先行，避免两套规则字面歧义。
- **落选**：回落 P2、前两期纯写入（北极星前两期不成立）；压缩时砍键盘路径或最简列表（违反已承诺验收与降级路线依赖）；两套压缩规则并存不声明优先级（实现期随机选一）。
- **落点**：规划 §7 P1（范围/验收/特例砍序）。

### 裁决 6（MVP）：源删除标注备份永久保留，不自动轮转

- **问题**：源删除自动备份的留存策略：EXPORTS_FOLDER 中的标注备份 JSON 是永久保留、还是保留最近 N 份/自动过期？
- **裁决**：永久保留，不做自动轮转。三条硬规则：① 文件名 `annotations-backup_{sourceId}_{YYYYMMDD-HHmmss}.json`；② 备份 JSON 内嵌 source 元数据快照（id/title/url/created/page_count）+ 全量标注，格式与 P2 JSON 导入器兼容（page_count 为复核新增，供导入预检）；③ 重访阈值：单备份 >50MB 或 EXPORTS_FOLDER 标注备份总量 >1GB 再议轮转，届时出 ADR。用户文档注明备份位于 exports 目录、随手动清理处理。（本轮复核无直接意见，维持拟定裁决；钩子落点与导入预检见裁决 8。）
- **理由**：已核实 `data_transfer_commands.py:87` EXPORTS_FOLDER 目录基建属实。611 页满标注量级数千条 × ~1KB ≈ 数 MB，磁盘压力可忽略；自动轮转与「误删防护」初衷直接冲突（发现误删时 N 份滚动可能已覆盖唯一备份）；与 data_export 明文同安全语义（自托管单用户）。
- **落选**：保留最近 N 份（误删久后发现时备份可能已被覆盖，防护失效）；30/90 天自动过期（与「痕迹是资产」相悖）；备份加密（与 data_export 不同级，制造安全语义分裂）。
- **落点**：规划 §1.2、§8#15。

### 裁决 7（P2）：遍次聚类——页码回退为主信号 + 时间阈值上调 7 天

- **问题**：「第 N 遍」遍次聚类的 72 小时间隔阈值是否贴合阅读节奏？P2 是否需要「手动开始新一遍」按钮？（产品复核 medium：OR 逻辑下 72h 单臂即可分遍，备考一遍中间隔 3 天空档即被误切，原「误判方向是合并」的断言不成立）
- **裁决**【复核修订】：新遍判定改为：页码回退 >100 页（主信号）OR 距上一条标注 ≥7 天（辅助信号，自 72h 上调）。其余维持：72h 表述废止；P2 不做「手动开始新一遍」按钮，列 P3 候选，触发条件 = dogfood 中遍次误分可感知；UI 维持弱化承诺（「约 N 遍」）。
- **理由**：采纳产品复核：原断言确实错误——OR 逻辑下时间臂单独触发分遍，72h 对以周计的备考周期太短，周末/生病/出差三天即误切。修订后主信号是页码回退（「从头重读」的真正语义信号），时间臂提到 7 天只处理「隔很久继续读」情形；7 天内断档+无回退不切遍，消解单臂误分。手动按钮维持后置（用户维护会话边界需要存储+编辑+删除语义，违背不建阅读会话表的轻量裁决）。
- **落选**：72h + OR（终稿原方案：断档 3 天即误分遍，「卖一个算错的数」风险放大）；AND 逻辑（时间+回退同时满足才分遍：「隔 30 天从 P300 继续读」和「隔 30 天从头重读」将无法区分，漏分遍）；P2 加手动开始新一遍按钮（重语义低频用）；AI 判遍次（违反「AI 使用必须明示」）。
- **落点**：规划 §6.1-B、§8#13、§10#8。

### 裁决 8（MVP）：钉死备份钩子落点 + 导入预检（恢复闭环拆两段）

- **问题**：【清扫】MVP 验收⑥「删除源后 EXPORTS_FOLDER 出现备份 JSON，恢复导入后标注可用」与 §6.3「JSON 导入 P2 尾交付、恢复到 id 一致的 source」双重断裂：MVP 期无导入器可执行验收；源已删除则原 id 已不存在。（技术复核 missing：备份钩子若在 API 路由层，notebook 独占删除级联会绕过备份；产品复核 missing：按 title 映射可命中同名不同版文件，缺导入前校验）

### 裁决 9（MVP）：display_position 三态语义（存量 NULL-with-body 跟随视图默认档）

- **问题**：【清扫】display_position 默认值三处矛盾：§2.2「默认 hover」vs §3.3「按视图区分默认档」vs §3.3 槽位列表内 hover 项残留「（默认）」标签；且存量 NULL-with-body 在 P1 后渲染语义未定义。（产品复核 medium：若固定 hover，MVP 期批注永远不进痕迹栏，恰好落进被自己否决的形态）

### 裁决 17（P1）：框选 quote 求交失败的降级出口 + 占位呈现规格

- **问题**：【清扫】§10#3「框选重锚靠 getTextContent 近似 quote 的命中率未知」无降级出口。（产品复核 low+missing：扫描主路径下 NULL 从第一天就必然击穿 >40% 阈值，事后触发形同虚设；且 quote-NULL 形态的总览/导出呈现样例缺失）
- **裁决**【复核修订】：① 求交为空或拼接结果不可打印/乱码字符占比 >30% 时 quote 存 NULL，不硬造引文；quote 为 NULL 的标注在总览/导出/复习手册统一占位格式：「[色方块][语义字] P.123 框选 · body 首行截断」（采纳产品复核 missing：给呈现规格，P1 dogfood 评审此形态的样例页，预判可读性）。② 采纳产品复核 low：换范围分支（框选为主路径）被激活时，quote 几乎必然全 NULL，>40% 事后触发形同虚设——该分支下不等触发，P1 dogfood 议程直接列入 quote 替身评估（优先评估框选区域 canvas 裁剪快照存数据文件夹作视觉替身；OCR 属新依赖走 VISION.md 的 PDR 流程），且该分支发布说明明示「框选标注读回以页码+批注为主，引文暂缺」。③ >40% 触发条件保留给非换范围情形（混排书扫描页 P1 框选交付后）。
- **理由**：采纳产品复核：已知必然击穿的阈值留在 dogfood 才讨论等于把已知结果当风险监控，前置到分支激活时的 dogfood 议程；canvas 快照评估优先于 OCR（无新依赖，与「引文快照」精神一致，但属评估非承诺——若采纳落 P2，需处理存储与导出包容）；占位格式给死消除实现期随机发挥。硬造坏 quote 会污染引文快照资产并在导出/转存笔记/手册三处外流，NULL+页码占位保持诚实。
- **落选**：无降级规则（坏引文流入资产与导出）；换范围分支仍等 >40% 触发（已知必破的阈值，讨论被无谓推迟）；扫描分支直接上 OCR（重依赖+新供应商语义，未经 PDR）；quote 留空且无占位格式（用户无法区分失数据与漏数据，样例缺席则实现期随机选一）。
- **落点**：规划 §5.3（quote 规则）、§8#17（新增风险行）、§10#3。

### 裁决 18（P1）：色语义改名编辑 UI 落 P1

- **问题**：【清扫，新增——回应一致性复核 missing】§4.2「语义（默认命名，可改名）」承诺悬空：annotation_settings GET/PUT 端点 MVP 交付，但 v1 各期范围与 MVP 任务清单均无改名编辑界面任务，「可改名」无 UI 入口。
- **裁决**【新增】：色语义改名编辑 UI 落 P1：「显示我的痕迹」开关所在工具栏区增设设置 popover（五色名编辑表单，读写 annotation_settings 端点），成本约 +0.25 人日并入 P1 既有「位置选项+开关 1 人日」项；MVP 期无 UI 入口为已接受状态——settings 端点 MVP 先行是数据主权裁决（服务端存储、localStorage 仅缓存），默认五色命名（重点/已掌握/疑问/参考/易错）在 MVP 期即可用，无入口不阻塞。
- **理由**：采纳一致性复核：端点与 UI 分期脱节属实。落 P1 而非 MVP：MVP 前端分项已 10-11 触顶，且默认命名在 MVP 期已可用（不违反验收）；P1 的开关/位置选项工具栏是天然入口，popover 复用 Popover 基建边际成本极低。若进 MVP 则挤占核心闭环，不划算。
- **落选**：维持无落点（「可改名」承诺悬空）；MVP 就做改名 UI（前端预算已触顶，且默认命名可用不阻塞验收）；砍掉「可改名」承诺改为固定命名（违反「机制通用、语义用户定义」的 §1.5 裁决）。
- **落点**：规划 §4.2、§7 P1。
